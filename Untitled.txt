## Integration reality

The biggest question is **where the live reservation and guest data comes from**.

There is a public-facing iTrip API index that lists available API method groups, including VRBO, Airbnb, BookingPal, Breezeway, FlipStream, v2, Partner, and Key Data. ([iTrip][1]) The iTrip Key Data API page specifically lists Properties and Bookings endpoints, which could be useful for the historical/performance and reservation-data side if access is approved. ([iTrip][2])

For guest messaging, Avochato is promising because it has an API and webhooks for sending and receiving SMS messages. ([Avochato Help Center][3]) Avochato’s API docs say API access uses account-specific Auth ID and Secret tokens generated from Settings > API Access. ([Avochato][4])

That means the clean architecture is:

```text
iTrip / KeyData API
        ↓
Reservation + Property Database
        ↓
AI App
        ↓
Staff Review
        ↓
Avochato / Email / Guest Messaging
```

I would **not** start by scraping `admin.iTrip.net` unless iTrip approves it. The better route is API access, scheduled exports, email reports, or a secure admin-approved integration.

# iTrip AI Command Center Plan

## Primary Goal

Create a private operations dashboard for iTrip-style property managers that can:

* Answer guest-service questions from property notes.
* Search property-specific details instantly.
* Analyze revenue, ADR, occupancy, and owner-block data.
* Build quote recommendations using historical performance.
* Show upcoming check-ins/check-outs.
* Draft guest replies using approved templates.
* Escalate risky guest messages to a human.
* Eventually integrate with guest messaging tools like Avochato or Hopper.

---

# Big Problem: No Reliable iTrip API

We should assume API access may be delayed, limited, expensive, or unavailable.

So the app should support **four data paths**:

## Data Path 1: Manual Upload

This is the fastest MVP.

Staff uploads:

* Revenue spreadsheets
* Occupancy spreadsheets
* ADR spreadsheets
* Owner block reports
* Reservation exports
* Property notes
* Check-in instruction docs
* Common response docs

Supported file types:

```text
.xlsx
.csv
.docx
.pdf
.txt
.json
```

This lets us build the first working version immediately.

---

## Data Path 2: Scheduled Email Import

If iTrip/admin reports can be emailed on a schedule, we can create a dedicated mailbox:

```text
reports@clientdomain.com
```

Then the app checks that inbox every few minutes or every hour.

Example workflow:

```text
iTrip/Admin Report Export
        ↓
Scheduled email to reports@clientdomain.com
        ↓
App reads attachment
        ↓
Parses CSV/XLSX/PDF
        ↓
Updates database
        ↓
AI dashboard refreshes
```

This avoids needing direct API access.

Good for:

* Daily arrivals
* Departures
* Occupancy reports
* Revenue reports
* Owner statements
* Reservation exports
* Maintenance/task reports

---

## Data Path 3: Browser-Assisted Export

If admin.iTrip.net has export buttons but no API, the staff can download reports manually.

The app would have an **Import Center**:

```text
Upload Today’s Arrivals Report
Upload This Month’s Occupancy Report
Upload Revenue Export
Upload Property List
Upload Guest Reservation Export
```

The system remembers column mappings after the first upload.

Example:

```text
Guest Name → guest_name
Arrival Date → check_in_date
Departure Date → check_out_date
Property → property_name
Phone → guest_phone
Email → guest_email
Reservation Total → total_revenue
```

This gives them value without any integration approval.

---

## Data Path 4: Secure Browser Automation

This is the fallback if reports are only visible inside admin.iTrip.net and cannot be exported automatically.

A small internal automation worker could:

* Log into admin.iTrip.net with approved credentials.
* Navigate to specific report pages.
* Download/export reports.
* Store files locally.
* Feed them into the app.

Tools:

```text
Playwright
Python
Scheduled Windows Task or Docker cron job
```

Important: this should only be used with client permission and should avoid scraping sensitive data unnecessarily.

This is not the first choice, but it gives us a path if there is no API and no automated exports.

# iTrip AI Command Center

## Phase 1 MVP

Build a private dashboard that works from uploaded files first.

### Included in MVP

```text
1. Login page
2. Dashboard overview
3. Import Center
4. Property Brain
5. Guest Reply Assistant
6. Revenue Analyst
7. Quote Builder prototype
8. Escalation classifier
```

### Data sources for MVP

```text
Property notes DOCX
Common response DOCX
Revenue XLSX
Occupancy XLSX
ADR XLSX
Reservation CSV/XLSX exports if available
```

### No-API fallback

```text
Manual upload first
Scheduled email import second
Browser export workflow third
Secure browser automation last
```

# What the app does first

## 1. Property Brain

Staff can ask:

```text
What is the Wi-Fi at 110 St. George?
Where does the guest park?
Where is the water shutoff?
Does this house have beach gear?
What should I tell a guest about trash pickup?
```

## 2. Guest Reply Assistant

Staff pastes a guest message and selects the property.

The AI returns:

```text
Suggested reply
Internal notes
Risk level
Whether manager approval is needed
Source documents used
```

## 3. Revenue Analyst

Staff can ask:

```text
Which properties made the most revenue?
What was the strongest month?
Which properties underperformed?
What does July look like compared to September?
```

## 4. Quote Builder

Staff enters:

```text
Property
Check-in date
Check-out date
Guest count
Repeat guest? yes/no
Direct booking? yes/no
```

The app returns:

```text
Conservative price
Recommended price
Aggressive price
Reasoning
Suggested guest message
Manager notes
```

# Next Step: Build the Demo Version

The demo should prove four things:

```text
1. The app can read their property documents.
2. The app can answer guest/property questions accurately.
3. The app can analyze revenue and occupancy spreadsheets.
4. The app can build a quote recommendation.
```

Do not start with Avochato, Hopper, or iTrip API yet. Those come after the demo.

# Step 2: Choose the First Build Type

You have two good options.

## Option A: Fast Prototype

Best for proving the idea quickly.

```text
Frontend: Streamlit
Backend: Python
Database: SQLite
Vector search: Chroma or Qdrant
AI: Gemini or local Ollama
File ingestion: DOCX + XLSX upload
```

Pros:

```text
Fastest to build
Easy to demo
Low cost
No complex frontend work
Perfect for proof of concept
```

Cons:

```text
Not as polished
Less like the PortfolioBay-style dashboard
```

---

## Option B: Real MVP Dashboard

Best if you want something closer to a real client-facing product.

```text
Frontend: Next.js / React
Backend: FastAPI
Database: PostgreSQL
Vector search: Qdrant
AI: Gemini or local Ollama
File ingestion: DOCX + XLSX upload
```

Pros:

```text
Looks professional
Scales better
Better long-term foundation
Can become the real app
```

Cons:

```text
Takes longer
More moving parts
```

---

# My Recommendation

Start with **Option A: Fast Prototype** first.

Reason:

```text
You already have sample files.
The goal is to prove value, not build the final platform yet.
A working demo will help sell the project and clarify what they actually need.
```

Then rebuild into Option B once the workflow is approved.
